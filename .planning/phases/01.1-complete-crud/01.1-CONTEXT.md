# Phase 1.1: Complete CRUD Operations — Context

## Domain
Add missing PUT/DELETE endpoints for clients, vehicles, parts, and work_orders. Wire frontend UI to use real API calls instead of no-op or missing operations.

## Goal (from ROADMAP)
Backend: PUT/DELETE `/clients/{id}`, PUT/DELETE `/vehicles/{id}`, PUT/DELETE `/parts/{id}`, DELETE `/work-orders/{id}`. Frontend: Wire update/delete in ClientsPage, WarehousePage.

## Decisions

### Deletion Strategy: Soft Delete
- **Clients** and **vehicles**: Add `is_deleted` boolean field (default `false`). On DELETE, set `is_deleted = true` instead of physical deletion. Filter out `is_deleted = true` from list queries. Detail endpoint returns 404 for soft-deleted items. This preserves order history while hiding archived records from UI.
- **Parts**: Also soft delete (same `is_deleted` field) because `part_movements` references parts.
- **Work orders**: Also soft delete (`is_deleted` field) because transactions and receipts reference orders. Alternative considered: hard delete since orders are transactional. **Decision**: soft delete to preserve financial history.

### Validation Schemas: Inline BaseModel
- Continue current pattern: define `BaseModel` subclasses inline within router handler files.
- Do NOT refactor to use `app/schemas/` — that is a separate cleanup phase.
- Keep schemas minimal: only fields that can be updated (e.g., don't expose `total_visits` on client update).

### Authentication
- **Do NOT add `get_current_user` dependency in this phase.** Auth enforcement is Phase 1.4.
- New endpoints remain open (same as existing ones).

### Frontend Behavior
- ClientsPage: Edit client modal → PUT `/clients/{id}`. Delete button → DELETE with confirmation dialog → invalidate queries.
- WarehousePage: Edit part modal → PUT `/parts/{id}`. Delete button → DELETE with confirmation.
- VehiclesPage: Edit vehicle modal → PUT `/vehicles/{id}`. Delete button → DELETE.
- WorkOrdersPage: Delete order button → DELETE with confirmation.

### Data Integrity
- Client delete: check if client has active (non-cancelled, non-deleted) work orders. If yes, return 409 with message.
- Vehicle delete: check if vehicle has active work orders. If yes, return 409.
- Part delete: check if part has linked movements. If yes, return 409.
- Work order delete: allow soft delete regardless of status (archived record).

## Code Context
- Existing routers use sync SQLAlchemy with `SessionLocal()` context manager.
- Client model: `name`, `phone`, `email`, `total_visits`, `total_revenue`, `last_visit` (auto-calculated).
- Vehicle model: `client_id`, `make`, `model`, `year`, `license_plate`, `vin`.
- Part model: `name`, `category`, `quantity`, `min_quantity`, `price`, `supplier`, `location`.
- Work order model: `client_id`, `vehicle_id`, `service_id`, `staff_id`, `status`, `total_cost`, `scheduled_date`, `completed_date`.
- Frontend uses TanStack Query with `queryClient.invalidateQueries()` for cache invalidation.
- API modules already define `update()` and `delete()` methods (calling PUT/DELETE) but backend endpoints don't exist.
