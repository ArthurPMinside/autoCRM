# Phase 1.2: Wire Warehouse & Marketing — Context

## Domain
Replace mock data with real API integration for Warehouse and Marketing pages. Add backend support for PartMovement tracking and full-featured marketing campaigns.

## Goal (from ROADMAP)
Backend: CRUD for PartMovement (write-off, restock, link to work order). Backend: Campaigns API. Frontend: Replace mockParts in WarehousePage and mockCampaigns in MarketingPage with real API calls.

## Decisions

### Warehouse: Tab-based UI
- WarehousePage gets two tabs: "Остатки" (inventory) and "История движений" (movement history)
- Clicking a part in the inventory table opens a side panel or modal showing part details + its movement history
- PartMovement table is filterable by part, type (in/out), date range

### PartMovement: Auto-update Quantity
- Creating a PartMovement automatically updates the Part.quantity:
  - type='in' (restock/return) → quantity += movement.quantity
  - type='out' (write-off/used_in_order) → quantity -= movement.quantity
- Movement record is the source of truth; quantity is a derived/cache field
- No separate endpoint to manually update quantity — always go through movement

### Marketing: Full-featured Campaigns
- Campaign model: name, description, status (active/completed/draft), start_date, end_date, budget, target_audience (JSON/text), source_code (for tracking)
- Campaign statistics: count of work_orders with matching source, total revenue from those orders
- Audience segmentation: simple filter-based (e.g., clients with X visits, last_visit before Y date)
- Message templates: name, channel (sms/email/telegram), body with placeholders
- Campaign execution: send messages to segmented audience via chosen channel

### Auth
- Do NOT add auth in this phase (Phase 1.4 handles it)
- New endpoints remain open

### Soft Delete Compatibility
- All new list endpoints MUST filter is_deleted=False
- PartMovement references parts — soft-deleted parts should still show in history but not be selectable for new movements
